# 密码重置蕴含邮箱验证（已否决）

**Status**: 已废弃 → **已明确否决**（2026-09-10）

本 ADR 曾提议：密码重置成功时顺带把 `emailVerifiedAt` 标记上。该行为从未落地，
现在也**确定不做**。当前行为：`emailVerifiedAt` 只由邮箱验证流程写入
（`verifyEmailOtp` 经 `consumeOtp` 的 onSuccess），密码重置不碰它。

> 沿革：原决策于 `a070113` 被 ADR-0002 推翻，ADR-0002 本身随后也被推翻
> （邮箱验证重新引入）。所以本 ADR 的「作用对象」回来了，但决策没有被重新采纳。
> 2026-09-10 复核后把「未决」改为「明确否决」。

## 原决策

账号可能处于「已注册但未验证邮箱」的状态，此时用户忘记密码。原提议是：
重置成功的同时把邮箱标记为已验证。理由有两条 ——

1. 能收到重置邮件本身就证明了邮箱所有权，与点击验证链接证明的是同一件事
2. 若重置后仍要求单独验证，用户「改完密码依然登录不了」，闭环出现裂缝

第 2 条还带出一个推论：拒绝这个决策会制造「改了密码却进不了门」的死锁体验。

## 为什么否决

**第 2 条论据不成立：那扇门根本没关。**

复核时逐处确认 —— `emailVerifiedAt` 不拦截任何操作：

```
login.functions.ts   0 处引用
guard.ts             0 处引用
其余写入点           无
消费方               仅 account.tsx / privacy-security.tsx 的显示徽章
```

未验证邮箱的用户**能正常登录、能改密码、能用全部功能**。「死锁」在当前实现里
并不存在，所以原决策要解决的问题本身是虚构的。

第 1 条论据（语义等价）也不够牢：

- 重置 OTP 证明的是「此刻能收到该邮箱的信」
- 邮箱验证证明的是「用户主动确认了这个地址属于自己」

两者不等价。而且一旦让 `emailVerifiedAt` 有两条产生路径，看数据就再也分不清
「真验证过」和「重置过」—— 一个字段一个含义值得守住。

**收益为 0（不拦任何操作）而代价是语义污染，故否决。**

## Consequences

- 用户重置密码后，设置页仍显示「邮箱未验证」—— **这是正确的**，他确实没验证过。
  若希望消除这个提示，正确做法是重置成功后**引导用户去完成邮箱验证**
  （跳到 `/auth/verify-email`），而不是替他假定已验证。两者区别在于：
  用户真的走完了验证，还是我们推断他应该算验证过。
- 若将来 `emailVerifiedAt` 真的变成一道门槛（比如未验证不得登录），
  本决策需要重新评估 —— 那时「死锁」才成为真问题。
- 写 `emailVerifiedAt` 的地方只有一处（`email-verification.ts`）。
  在别处看到写入 `emailVerifiedAt` 时，先怀疑是不是引入了第二条语义。
